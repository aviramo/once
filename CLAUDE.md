## Three worlds: `users.env` (`il` / `review` / `dev`)

**The environment an account lives in is `users.env`, and the first GPS fix decides it** (user directive 2026-08-13). `il` is production — an account whose first location fell inside **`_in_home_region`: Israel, Jordan and Lebanon**, three rectangles rather than one so that Damascus falls outside (a single box wide enough for northern Lebanon and eastern Jordan takes southern Syria with it). `review` is everyone else, **and its purpose is to isolate the App Store reviewers**, who are the ones the seeded pool around Apple's campuses was built for. `dev` is the Hebrew test cast and the developer's own devices, which used to share a partition with the reviewers — that is why a boolean was not enough. The region opened as the whole Middle East and was narrowed the same day; widening it again means putting whoever it lets in into the Israeli pool, so it is a product decision, never a tidy-up.

- **Decided ONCE.** `_users_env_stamp` (BEFORE INSERT OR UPDATE on `users`) reads the location only while `data.env_locked_at` is absent, then stamps the lock. A traveller does not move; a spoofed simulator does not move; every account that existed on 2026-08-13 was stamped in the state it was already in. The one way to move an account afterwards is **`app_admin_set_env(user_id, env)`**, which releases both boards first (a live watch/invite/chat may never straddle two worlds) and takes the circles the account owns with it.
- **No location yet → `review`** (the column default). Unknown fails towards the world that cannot reach an Israeli user.
- **`is_test` STAYS, derived** (`env <> 'il'`, written by that same trigger) because the admin console and helpers like `_is_test` still read it. **Never write `is_test` by hand — it is overwritten from `env`.**
- **Every partition check compares `env`**: `others()` (the sole candidacy chokepoint), `_same_partition` (friends, friend links by code, reports, referrals, people search), `app_search_groups`, `app_redeem_invite`, `app_respond_join`, `_group_drain_requests`. `groups.env` is stamped from the owner by `_group_stamp_is_test`. Adding a new cross-user path means adding an `env` check to it.

## Real users (`env = 'il'`) — stop and confirm

Every DB write that would touch a row belonging to a real user — one where `users.env = 'il'` (equivalently `is_test = false`), or any row keyed to that user in `chat` / `chat_reads` / `restrictions` / `states` / `groups` / `user_groups` / `friend_links` / `friend_requests` / `group_join_requests` / `referrals` / `log` — is a **halt point**. Before executing, list the affected users and rows and get explicit approval, even when the request sounds like a routine test-data operation. Scripts scoped to `env IN ('review','dev')` run without asking. When a query filter is `name ILIKE …` or `IN (…)` and could sweep in real accounts by accident, add an explicit `AND env <> 'il'` guard and mention doing so. This applies to `UPDATE`, `DELETE`, and to any RPC that would mutate that user's state — reads are always fine.

## The App Store review world (temporary)

The `review` world is seeded: 103 English accounts marked `users.data->>'seed' = 'app-store-review'` (that marker, never a name list) in 22 circles, laid out around Apple's campuses, built by `scripts/appstore-seed/`. Three server rules hold it up, all scoped to that marker and **all to be removed once a build cut after `a15a0f4` is live**:
- **`review-pool-touch`** (pg_cron, every 5 min) — `others()` only offers somebody seen within a day, and these are rows rather than phones, so a random stale handful is marked seen a few minutes ago.
- **`review-pool-answer`** (pg_cron, every minute) — accepts, through `app_approve` itself, every invitation aimed at a pool account 10 seconds after it was sent, and opens the chat with one line. An invitation there may never be left to expire.
- **`watch_review_swallow_ended`** (BEFORE trigger on `watch`) — stamps `watcher_cleared_at`/`target_cleared_at` as any relation with a pool account ends, so no ended card is drawn. **This one is a workaround for a shipped bug**: the store build (`ed8afa2`) renamed its ended-state lookups to `home.locked.watch.*` / `home.locked.invite.*` one commit before `he.ts`/`en.ts` followed, and `t()`/`tg()` return the KEY itself when it is missing, so all thirteen endings paint the raw key on the heading chip and in the message popup. Delete the trigger the day the fixed build is live.

## UI layout iron rules (`mobile/app/home.tsx`)

Absolute; apply whenever the shell or overlays are touched.

**One screen: page1 (home).** `page1`/`page2` are server data-model terms only — they are **not** separate screens. Everything else rises over home as a full-screen `OverlaySheet`, dismissed by swiping down. There is **no pager, no tab strip, no horizontal navigation.** `TabStrip.tsx`, `HomeCard.tsx`, `WatcherCard.tsx` are deleted — do not resurrect them.

**One swipe-down implementation: `mobile/src/components/PullPane.tsx`** (`PullContext`/`PullScrollView`/`usePullBehavior`/`PullPane`). It is THE "drag a surface with the finger" mechanism — page1's pull-to-skip, the invite's pull-to-decline, and every overlay's swipe-to-close are the same code. **Never hand-roll a second `Gesture.Pan` for a swipe-down.**
- `usePullBehavior` `axis`: `'y'` (default) = off the bottom; `'x'` = off the START edge. `pullY` is always ≥ 0 magnitude; only `PullPane`'s transform knows physical direction (`AXIS_X_SIGN`, flips under RTL). **`'x'` currently has NO call site** — the menu drawer was its only one and was deleted 2026-07-30. The machinery is still wired end-to-end (`PullAxis`, `OverlaySheet`'s `axis`, `RisingCard`'s `from="side"`, the header's back-arrow glyph); it is dead weight on the app's one gesture path and should be removed in a change of its own, not folded into an unrelated edit.
- `commit`: `'slideOff'` (default) rides the surface off then fires `onCommit`; `'snapBack'` fires `onCommit` first then springs home. **`'snapBack'` is live again** (user directive 2026-08-01) and it is what "the drag ASKS" is built on — see "A pull in every state" below. Unlike the `'x'` axis, which is still dead weight, this one now has three call sites.
- **HOW FAR A PULL MUST TRAVEL IS DECIDED BY WHAT LETTING GO *DOES*, NEVER BY WHICH ACTIVATION IT USES** (user report 2026-08-02: closing a circle's settings page and closing chat both took work). `usePullBehavior`'s **`weight`**, and there are exactly two: **`'decide'`** — half the screen (`PULL_COMMIT_FRACTION`) and NO flick, because the release ANSWERS something about the person on the card and may never be made by speed (user: "regardless of swipe speed, only if the finger and the card together passed the half"); and **`'close'`**, the default — a fifth (`PULL_CLOSE_FRACTION`) or a flick, because the surface merely goes away. Putting a page away is reversible and must cost what putting a popup away costs: a `BottomSheet` dismisses at `SWIPE_DISMISS_PX` (80) and a full-screen page was asking for ~420px, which reads as the swipe not working rather than as a guard. **Two call sites state `'decide'` and no others may**: home's page1 card (all of its states at once, so the gate cannot change under the user as the card changes — and so the name-slide, which normalizes against `commitDistance`, keeps its calibration) and an `OverlaySheet` whose `commit` is `'confirm'`, which is the invitation asking a question. It is deliberately NOT derived from `activation` or `commit`: page1's skip is a `'slideOff'` that decides, and a Circles profile page is a `'scrollPan'` that only closes — only the call site knows which its pull is.
- **A SURFACE THAT UNMOUNTS WHEN THE RIDE-OFF LANDS MUST WATCH BOTH FACTS AT ONCE.** `onCommit` is a `runOnJS` out of the gesture's `onEnd`, so the "I am closing" flag is set on the JS thread while the ride-off runs on the UI thread: on a busy JS thread the flag lands **after** `pullY` has already stopped at `screenSpan`. A reaction whose prepare reads only `pullY` then never fires again — nothing moves after an animation ends — and the surface stays mounted, parked off-screen and invisible, but still the TOP layer, which kills the swipe of the page under it (`enabled: isTop`), its `commit()` (an early return on `slidOut`) and hardware back with it. So the prepare returns `closing && pullY >= screenSpan` — whichever of the two arrives last is what fires the unmount. `CirclesPage`'s `PageLayer` is the app's only surface built this way (the lightbox and page1's name-slide watch `pullY` alone and are gated on nothing); it went unresponsive on the emulator on 2026-07-31, after popping a member's page.
- **THE INNER SCROLL ALWAYS OUTRANKS THE PULL** (user directive 2026-07-27, absolute). A finger on scrollable content scrolls it; the pull takes the surface only where the scroll has nothing left to give, and it takes over **mid-gesture** (`scrollSpent` re-origins the pull the frame the list bottoms out at its top, so one drag scrolls to the top and carries straight on into the close). `usePullBehavior`'s `headerBottom` band — the one thing that overrides the at-top flag — may therefore only ever cover chrome that **cannot scroll**: a solid title bar, a fixed head above a list. Never a header that FLOATS over scrollable content, never a slice of the scroll itself. The single exception is `dragFrom="header"`, for a body whose scroll genuinely cannot report at-top (chat's inverted `FlatList`), and even there the body refines the flag itself.
- **Nothing re-renders because a drag started.** The "a pull is happening" signal is the `pullEngaged` **shared value** on `PullCtx`, never a React boolean threaded down to a page: a commit landing on a running gesture is what made swipe-closes stutter. `PullScrollView` is the only component that turns it back into state (it must change a native prop), and its children are untouched elements, so React bails out below it. `usePullBehavior`'s `pulling` boolean is maintained for `'scrollPan'` **only**, for page1's name-slide, which genuinely needs a render.
- **Every release continues the finger.** A committed pull rides off on `RIDE_OFF` (`Easing.out(cubic)`) and a snap-back is `withSpring` seeded with the release velocity (`PULL_SNAP_SPRING`) — never a bare `withTiming`, whose ease-IN makes the surface hang for a beat before it moves. The pull also opens from where the finger IS at activation (`pullBase`), never jumping by the arbitration slop.
- `BottomSheet.tsx` keeps its own separate swipe-to-dismiss for small bottom-anchored dialogs — deliberately a different gesture; do not merge them.

**`OverlaySheet.tsx` is the only bottom-up surface** (`PullPane` + `usePullBehavior` + `RisingCard` + `SheetHeader`). **A sheet's close X sits at the top-END** (user directive 2026-07-30, in `SheetHeader`): it was at the START for as long as home's hamburger was, so that opening a sheet turned one into the other without either moving — the hamburger is gone and the card's heading tile stands in that corner now, so the X moved across rather than the heading being pushed out of the corner it reads from. `trailing` takes whichever column the X does not, and that one is the droppable one (a `center` with nothing beside it takes the whole span). The `back` arrow of an `axis='x'` drawer is the one exception and stays at the START — a back arrow points at the edge it returns to — though that axis still has no call site.
  **AND THE X ITSELF IS DROPPABLE: `onClose` OMITTED = NO DISMISS AT ALL** (user directive 2026-07-31). **NO OverlaySheet IN THE APP WEARS ONE ANY MORE** — the one X left is the chat image lightbox's, which is a raw `Modal`, not a sheet. A surface the user opened by hand already leaves the way he opened it — the swipe, and hardware back through it — so a button repeating that is chrome saying what the gesture already does. Three went that day: **every Communities page** (`SheetHeader` with no `onClose`; see the Communities note below); the **Profile preview**, whose sheet is `chromeless` now rather than `floatingHeader` — its body is a full-bleed card of my own photos and the one mark over it, the heading tile's plus, is something to DO, so a dismiss floating beside it made that corner read as two unrelated marks (`PreviewFieldPage` lost its `onBack` prop with it — it never called it — and `SelfProfileRenderer` its `onBack` field, so the page has no way out to wire wrongly; `home.a11y.closeProfile` is deleted); and **CHAT**, which is the one that keeps its header ROW.   **AND SINCE 2026-08-02 THAT BAND SAYS SO — IT WEARS THE APP'S DRAG HANDLE** (user directive). Dragging the top strip is the ONLY way out of a LONG conversation (a body drag mid-history is scroll, by design, and hardware back is Android's alone), and with nothing painted on that line the user was looking at a screen of bubbles running to the very top edge with no reason to believe there was a handle above them — a way out that works always and is advertised nowhere. **The X does not come back** for it: a handle MARKS the gesture the sheet already has, where a button would be a second way out saying what the gesture says. It is `OverlaySheet`'s **`dragHandle`** → `SheetHeader`'s, taking the TITLE's slot (so it is mutually exclusive with a title by construction) and standing on the row's own chrome line, the height a dismiss circle occupies. **One handle in the app: `mobile/src/components/DragHandle.tsx`** — the bar every `BottomSheet` carries at the top of its card, and this. It is DECORATION and never a target (`pointerEvents:'none'`): the drag belongs to the band's own pan, and a handle that swallowed its own touch would be a smaller drag area than the band it advertises. It carries no spacing of its own — where it stands is the host's. **The BAR IS BARE, AND WHAT MAKES IT LEGIBLE IS A BAND, NEVER A TILE** (user directive 2026-08-02). Chat is `topInset={0}`, so bubbles scroll right under that row, and `INK_DIM` vanishes on an outgoing `INK` bubble exactly as white would vanish on an incoming one — the very trap that drove chat's typing pill out of the row's centre the same day. The first answer was the app's floating-chrome tile (`PHOTO_CHROME` + `LIFT_SHADOW`, how the X on this row used to stay legible) and it was rejected on sight: a white capsule around 48×4 of ink reads as a chip that has lost its label. So the ground is the **PAGE's own**, run the full width across the top of the sheet and then MELTED into the body — the handle stands on the page, and the band has no edge that could read as a bar of chrome. **Two pieces and no measurement between them**: a solid `PAGE` box and a fade hung off its bottom edge (`top:'100%'`) carrying that same colour out to nothing, so the pair stays honest at any header height and font scale. **It is NOT the header row's own box, and it is HALF STRENGTH** (user directive 2026-08-02). The row is the DRAG area and is a whole chrome circle tall (`headerFloor`); as PAINT that is a slab of page tint over the top of the conversation. What has to be covered is the BAR, so the solid part ends just under it (`handleBandHeight` — the handle's own line, being centred in `ROUND_BUTTON_SIZE_SM`, plus its thickness) and the fade is half a `SCROLL_FADE`. Paint and touch are independent here, so shrinking the band takes nothing off the gesture. `HANDLE_BAND_ALPHA` (0.5) is stated once, on the BOX, so the solid part and its fade can never disagree about the strength they start from — at full `PAGE` the thing read as a bar of chrome pasted over the chat, which is the one thing it must not be. That is the same fade vocabulary a popup already uses where content runs past an edge, which is why it is not the app's no-gradients rule being bent. The card is still not a surface the user OPENED — it is the app asking him something — which is why it has no X and why the drag may never answer for him. Load-bearing details: `pull.reset()` on every open (a slid-off close parks `pullY` off-screen); `dragFrom="header"` for chat (its `FlatList` is inverted so "at top" is meaningless) — but `ChatPage` receives the sheet's `sheetBody` ctx and drives the at-top flag itself (`syncScrollability`) so a body swipe-down closes the sheet in the cases where a downward drag genuinely can't scroll: (a) the list is empty or its content fits the viewport, and (b) the list is scrolled to the OLDEST end (the inverted list's max offset / visual top) with nothing more to page in — the "reached the top and keep pulling" pull-to-close. **ANSWERING AN INVITATION OPENS A CHAT, AND THAT IS ALL THERE IS TO SEE** (user directive 2026-08-02: "from the user's side a chat should open, that is all; and when he closes it he should see the profile he approved"). What he saw instead — measured on the emulator, frame by frame — was FOUR screens over two and a half seconds, because **the accept is not one event**: the server writes the board through the `watch` rows, every one of those writes is projected onto `users.relations` on its own and broadcast on its own, so the client is handed the transition in stages — page1 empties (the card he was watching slides out), then page2 empties and **home is BARE, play button and all**, then page1 becomes the chat, and only then does the sheet rise. Not one of those middle screens is a state the user was ever in. So the card he ANSWERED is what stays on the screen for the whole of it: **`answeredInvite`** in `home.tsx`, set by the accept and read by `page2PendingInvite`, which every page2 surface already draws from — the clock, the round action, the chip's mark, the sheet — so the held card is the card he was looking at in every respect, not a copy that has to be kept in step. Home's page1 swap and the invite sheet's ride-off both happen behind it, unseen. **It is keyed on the ANSWER and never on the state**, precisely because the states in between are the thing being hidden: no arrangement of `relations` can release it early, and nothing but an accept can arm it. **The accept popup is held by the same fact** and keeps its spinner (`busy` / `acceptLoading` read `answeredInvite`), so the whole transition is the app plainly working and then a conversation, and there is never a live accept button on a card that has already been answered. Four things end the hold and nothing else may: the chat sheet LANDING (**`onArrived`** on `OverlaySheet`, and under it on `RisingCard` — whoever owns the rise owns the announcement: a `keepMounted` sheet from its own park timing, a mount/unmount one from `RisingCard`'s entrance, a card born arrived on mount, never a duration copied into a timer; `finished` is not consulted, exactly as `RisingCard`'s entrance does not consult it); the request coming back a REFUSAL (`runAction` hands its `onDone` an `ok` — the RPCs' own refusals are 400s — because there is no chat coming and the server has already replaced the card); the overlay GATE, which force-closes chat so nothing will ever rise; and `ANSWER_HOLD_MAX_MS` (15s), the backstop under the routes nobody can name. **The server still broadcasts those intermediate boards** — the INVITER's side gets the same gap, page1 waiting → empty → chat, with no answered card to hold over it — and the fix at the source is one projection per transaction (`_watch_project` is a per-row `AFTER` trigger on `watch`; 21 of the 26 writers already call it explicitly at the end), which is NOT done.

**The chat composer is ONE box, and both of its controls stand INSIDE it** (user directive 2026-07-30). The field (`inputWrap` in `mobile/app/chat.tsx`) is the whole width of the row; nothing sits beside it. ## Keyboard — the page shrinks, in TWO places, and nowhere else

**The keyboard shrinks the page** (user directive 2026-07-30, absolute). The bottom of the page is flush against the top of the keyboard at every instant, going up and coming down — it *rides* the keyboard, it does not jump to where the keyboard will end up. **No screen, popup, list or component knows a keyboard exists**; each one is simply laid out in a box that got shorter. This replaces the per-screen-nudge regime of 2026-05-19, and with it the eleven separate patches that regime grew (four hand-rolled `Keyboard.addListener` height trackers and seven `marginBottom` call sites, each computing the height slightly differently).

**One module: `mobile/src/hooks/useKeyboard.ts`.** It is the only file in the app allowed to import `react-native-keyboard-controller`. `useKeyboardShrinkSV()` is the one value a surface may lay itself out against — **layout only**, a shared value updated every frame of the keyboard's movement: the keyboard's height less half the app's bottom air (see below). The raw height is module-private, because a surface that reads it holds none of the air rule. `useKeyboardOpen()` is a JS boolean for logic that must re-render, one flip per open and one per close (its two edges are deliberately asymmetric — see the hook). `useKeyboardReveal()` is wired into `PullScrollView` and belongs to nobody else.

Why that library and not RN's `Keyboard` events or Reanimated's `useAnimatedKeyboard`: it is the only one that reports the keyboard frame by frame from the platform's own animation, which is what "flush at every instant" requires, and RN's events have a blind spot the app has already been bitten by — they do not fire when a keyboard that is **already up** merely changes height under the same focused field, so Gboard swapping to its taller emoji panel buried the chat composer (2026-07-29).

**Exactly TWO application points, because the app has exactly two native windows:**
1. **`mobile/app/_layout.tsx`** — `KeyboardShrink` wraps the `<Stack>` in a `paddingBottom` driven by `useKeyboardShrinkSV()`. Covers every route and every `OverlaySheet` (they are `absoluteFill` children of home's shell). `KeyboardProvider` sits above it with `statusBarTranslucent`/`navigationBarTranslucent`/`preserveEdgeToEdge` passed explicitly, which is what makes the reported height the **full** `WindowInsets.ime()` inset rather than the navigation-bar-subtracted one.

   It shrinks by **`useKeyboardShrinkSV()`** — the keyboard's height less **half the app's bottom air** (`keyboardAirCut`, tokens.ts; user directive 2026-07-30). The keyboard is one more piece of system furniture at the bottom of the window, like the navigation bar and the home indicator, so the page stops where the furniture starts; but the air exists to keep chrome off the system's bottom band, and a keyboard covers that band, so half of it is enough. **Every bottom-anchored control therefore ends `bottomGap(...)` above the screen edge and HALF that above the keyboard, on every device and both platforms.** Both application points consume that one hook — do not let the page and the popup compute a lift of their own. It used to subtract `useBottomInset()` here instead, on the same "the band is dead space" reasoning, and that was the bug: `bottomGap` is a `max`, so on a device whose band exceeds the design gap (every iPhone: 34 against a composer's SM) the band IS the control's whole air, and cancelling it deleted the air rather than the dead space — the composer sat flush on the keyboard ("the gap was destroyed, there is no consistency", iPhone) — while subtracting a DEVICE number also made the result differ per platform. The cut is a design value now. Cancelling at the source instead — a `useBottomInset()` that returns 0 while the keyboard is open — is worse still: a React state flip, i.e. a **~60px step** at each end of the animation ("two noticeable stages", same day). **Nothing may re-render because the keyboard moved.**
2. **`mobile/src/components/BottomSheet.tsx`** — a RN `Modal` is its own window and inherits nothing from the root, so **the popup lifts itself**, once, for all fourteen popups: `marginBottom` on the card wrap plus `flexShrink` on the wrap and the card, so the keyboard's height is taken *out of* the room the sheet may occupy and a tall sheet gives at its `<SheetScroll>` instead of growing off the top of the screen.

**Forbidden anywhere else:** a `Keyboard.addListener` that reads a height, `KeyboardAvoidingView`, `keyboardVerticalOffset`, a keyboard `marginBottom`/`paddingBottom` at a call site, a second `useResizeMode()` (it restores the default input mode on unmount, so a caller that unmounts takes it away from the app), and a popup hand-rolled from a raw `Modal`. Compose `BottomSheet`/`ConfirmDialog`; add a text field via `ConfirmDialog`'s `noteInput`. A new sheet with a focusable input needs **no keyboard code at all**. (`Keyboard.dismiss()` is untouched by all of this and stays.)

**Shrinking is only half the job — `PullScrollView` does the other half.** A field low on the page ends up below the fold of the shorter page, and no amount of shrinking brings it back; only the content moving does. `useKeyboardReveal` is declared once on `PullScrollView` for the same reason `keyboardDismissMode` is: it is the app's only scroll surface, so one declaration covers every list and form. It fires on the keyboard's `onEnd` (measuring before the shrink lands measures the wrong page) and **also** when focus moves between fields while the keyboard is already up, which moves no keyboard and would otherwise fire nothing (the age popup chains from → to, onboarding chains three date fields). Every surface runs it, so the one the field actually lives in identifies itself by comparing the native `parentScrollViewTarget` against its own node handle — without that, a keyboard opening over a popup would also scroll the list behind it.

**THE KEYBOARD NEVER RE-MEASURES A BOX THAT JS MEASURED** (2026-07-30). The shrink is a shared value on the root's padding, i.e. a layout change committed on the UI thread — what reaches JS is an unreliable trickle of `onLayout` events, not a value per frame ending on the truth, so a box that sizes itself from `onLayout` can be left holding a mid-animation FRAME of a keyboard that has already gone. `MatchCard` was: its `cardH` (and with it every photo's height) stuck at an intermediate value, painting two photos in one screen with the action bar crammed under them (Pixel; the emulator never showed it). So the card's onLayout is **rejected while `useKeyboardOpen()`** — the last measurement taken with the keyboard down IS the full height, so there is nothing to restore afterwards. **A shorter window crops a surface; it never resizes it.** Same rule, same reason, as `onboarding`'s `measuredOnceRef`, which freezes its step height at first layout. `MatchCard`'s re-pin (`photoPageRef * photoHeight` on a page-height change, skipped while the bio is focused) now covers only genuine box changes — the action bar under the card appearing or going away — and no longer the keyboard.

**THE KEYBOARD GOING AWAY ENDS THE EDIT, AND NOTHING ON THE PAGE IS LIVE UNTIL IT DOES** (user directive 2026-07-30). BACK, the IME's own hide key and a tap outside the field all close an inline editor, and **only the third goes through JS** (`Keyboard.dismiss()`, which blurs) — the other two are handled by the IME and never reach the app, so they left the field FOCUSED, caret and Update footer standing under a keyboard that was gone: the app believing the edit was over (paging back on, taps live again) while the platform believed it was still running. So **`EditableText` blurs itself when the keyboard leaves**, once, for the bio and all three group editors; leaving without Update discards the draft, by every route identically (nothing is ever saved on blur). And while an edit IS open a tap anywhere ends it and does **nothing else** — the card swallows its own (`swallowTapWhileEditing`), and `ProfileActionBar` wears a lid over the whole bar, being the one thing on a profile page that is not the card.

**SCROLLING NEVER CLOSES THE KEYBOARD; ONLY A TAP OUTSIDE A TEXT BOX DOES** (user directive 2026-07-30, absolute, and it *replaces* the `on-drag` rule of 2026-07-29 — do not restore that one). While a field is focused the user may scroll the page freely and the field stays in edit mode. It applies to **every** text field in the app, with no per-screen exceptions.

The old rule made a covered field unreachable: scrolling is the only way to bring something out from under the keyboard, and scrolling was the thing that tore the edit down (the group link, 2026-07-30).

**Declared once, in `PullScrollView`** (`mobile/src/components/PullPane.tsx`) — the app's only scroll wrapper — as the two halves of one rule, which travel together: `keyboardDismissMode="none"` and `keyboardShouldPersistTaps="handled"`. The second is what makes "tap outside" work at all: a tap a child handles (a row, a button) leaves the keyboard alone; a tap nothing handles — the background — closes it. **Never set either at a call site.** `BottomSheet`'s `<SheetScroll>` repeats `keyboardShouldPersistTaps` because it is the one field-bearing scroll that is not a `PullScrollView`; a popup body's own plain `ScrollView` must do the same.

Alongside it: a Communities page's ROOT dismisses on a background tap (`TouchableWithoutFeedback`, never `Pressable` — its `pressed` state would re-render the whole page for a press that draws nothing), and `MatchCard` swallows a tap outside the focused bio the same way. The one place a gesture still dismisses is onboarding's swipe-back between steps (`onPanResponderGrant`), which is navigation away from the field rather than scrolling — the field is leaving the screen either way.

**NOTHING IS FOCUSED INTO A SURFACE THAT IS STILL ARRIVING** (2026-07-30). The platform measures a focused field exactly ONCE, when it takes focus (Android's `FocusedInputObserver` syncs on the focus event and on the field's OWN layout — an ancestor sliding under it is neither), and every consumer reads that one number for as long as the field keeps focus. A field focused mid-entrance therefore reports the position it had while flying, and reports it forever: the create-group form auto-focused its name field while the page was still rising, `useKeyboardReveal` measured that field as sitting off the bottom of the screen and scrolled the form to its last row to "reveal" it, leaving the field being typed in above the top of the page (Pixel; it needs a real device's rise-against-IME timing, which is why the emulator never showed it). So `autoFocus` on `AppText`'s `TextInput` means **"focus when my surface has arrived"** — inside a `RisingCard` it waits for the entrance's own completion callback (`RiseArrival` / `useRiseArrived`, `RisingCard.tsx`), everywhere else it is the platform's own, untouched. **Never compensate for a stale measurement inside `useKeyboard.ts`** — every number it could be corrected against is stale in the same way — and never hand a raw RN `TextInput` an `autoFocus` at a call site.

**THE REVEAL CLEARS THE SURFACE'S OWN BOTTOM, NEVER THE KEYBOARD'S TOP** (2026-07-30). Most scroll surfaces in the app *are* the page, so the two are the same line — but a surface with fixed chrome under it is not: the profile preview was a card with `ProfileActionBar` beneath it, so its scroll ended a bar's height above the keyboard, and a reveal aimed at the keyboard lifted the bio field into the strip the card cannot show. (That preview has no bar since 2026-07-31 — see the heading plus — but a communities person page still stands on one, and the rule is about any surface that does not reach the keyboard.) Reads exactly like the keyboard covering the field. `visibleBottomFor` in `useKeyboardReveal` measures the surface and subtracts the shrink it is about to take (`min` with the keyboard's top, so a full-page surface is unchanged). A surface that does not reach the keyboard must never pretend it does.

**A control with chrome UNDER its input must declare it.** The platform reports only the `TextInput`'s own frame, so the reveal clears only that: `EditableText` grows a footer holding its Update button — the only save path — the instant it takes focus, and revealing just the input left that button behind the keyboard. `useFocusedFieldFooter(height, active)` (`src/hooks/useKeyboard.ts`) is how a control adds its own chrome to what must stay visible.

## Bottom safe area — `useBottomInset()`, never `useSafeAreaInsets().bottom`

Single source of the bottom system inset: **`useBottomInset()`** (`mobile/src/hooks/useBottomInset.ts`), always paired with `bottomGap()`. The app draws edge-to-edge, so the navigation bar is painted OVER the content and the inset is what says whether bottom-anchored chrome would be clipped by it — but the live inset is not trustworthy: an IME session can zero it while the window is back at full height, and everything anchored to the bottom then lands inside the navigation bar (2026-07-29: the match card's report + chat buttons came back sliced in half on a 3-button-nav Redmi). The hook returns the session's high-water mark, seeded from `initialWindowMetrics`. `useSafeAreaInsets()` stays in use for `.top` only.

**ONE bottom air, the same on every device** (user directive 2026-07-30). The device's band is NOT the air, and `bottomGap` (tokens.ts) no longer treats it as one: an iPhone reports 34 for its home indicator and Android 16–24 for its gesture pill, so absorbing the design gap into the band gave the same surface **twice** the gap on iPhone — two device numbers, neither of them the design's. The band is now read for one thing only, whether it is furniture the app would be clipped by, and its own size is the answer: at or under `BOTTOM_BAND_HINT_MAX` (XL) it is a HINT — an indicator or a gesture pill, marking a gesture zone and occupying nothing — cleared by the app's own `BOTTOM_AIR` (LG), identical on every such device; taller than that it is a drawn navigation BAR (48, Android 3-button) and is cleared **in full**, which is the case that must never be capped (the Redmi above). The `gap` argument is a FLOOR: a surface wanting more air (a list's XL) keeps it, one asking for less is lifted to the app's air.

**The air is HALVED while the keyboard is up, and only there** (user directive 2026-07-30): the air is what keeps chrome off the system's bottom band, a keyboard covers that band, so a control keeps `bottomGap(...)/2` over a keyboard and the whole of it over the band. It is applied ONCE, as `keyboardAirCut` inside `useKeyboardShrinkSV()` (the two keyboard application points), never at a call site — **this hook knows nothing about the keyboard and must not learn.** Two dead ends, recorded so neither returns: returning 0 here while the keyboard is up is a React state flip, i.e. a ~60px step at each end of the animation (measured 2026-07-30); and subtracting *this* value from the shrink was continuous but cancelled the control's whole air and did it by a different amount per platform (see application point 1). The cut belongs to the design, not to the device.

**A POPUP's bottom gap is `BottomSheet`'s, never a call site's** (user directive 2026-07-29). Every popup ends the same distance above the screen: `bottomGap(useBottomInset(), LG)`, declared once on `BottomSheet`'s card and applied **after** `contentStyle`, so a body style physically cannot differ. The card used to declare no bottom padding at all and each of the fourteen call sites invented its own (`LG` in `ConfirmDialog`, `MD` on the group and shared-lists popups, `XL` on the select lists, three different `bottomGap(...)` values in settings) — that is why the credits popup and the group popup ended at different heights. A popup body therefore sets **no** padding at all beyond the exceptions below, and an inner `ScrollView` inside one adds **no** `paddingBottom` of its own: the sheet's gap already sits under it.

## Every popup is the popup, and its FOUR gaps are one set of tokens

**Every popup in the app is `BottomSheet`** (`mobile/src/components/BottomSheet.tsx`) — or `ConfirmDialog`, which composes it — and it is the ONLY bottom-anchored dialog. Never a raw `Modal`, never a hand-rolled title/description/button column. Two raw `Modal`s are left and neither is a popup: chat's full-screen image viewer, which is a lightbox, and **`TapMenu.tsx`** below. A popup's parts are components, not copied styles: **`SheetTitle`** (the heading, `SHEET_TITLE`), **`SheetDesc`** (the sentence under it, `SHEET_DESC`), **`SheetActions`** (the buttons at the foot; `row` for a cancel/confirm pair, `flush` for a sheet that is nothing but buttons), **`SheetActionPair`** (below), **`SheetActionRow`** (one tinted choice tile), **`SheetScroll`** (the one block allowed to run long).

**EVERY `ConfirmDialog` IS THE ORDINARY POPUP, AND IT HAS EXACTLY ONE BUTTON** (user directive 2026-07-31). The drag handle, the swipe-down and the backdrop tap are `BottomSheet`'s own defaults and `ConfirmDialog` now overrides none of them. They used to be opt-in behind a **`draggable`** prop that all fifteen call sites passed and **one did not** — onboarding's birthdate confirmation, which therefore rose with no handle over its title and could not be put away by hand, so the app's most standard surface was its one deviation ("why is it different? why is there no standard?"). A prop every call site passes is not a choice: it is deleted, and a dialog physically cannot come up undismissable again. **AND THERE IS NO CANCEL BUTTON ANYWHERE IN THE APP**: putting the popup away IS the cancel — what it would take you back to is still on the page behind it — so the one thing to press is the thing the popup is asking for. Onboarding's "Fix" was the last one and is gone with its `ob.birthConfirmFix` string; `cancelLabel` still renders one for a caller that genuinely needs that answer NAMED, and nothing in the app uses it. Do not reintroduce `draggable`, and do not answer a "there should be two buttons" instinct with one.

**THE PURPLE IS ALWAYS LAST** (user directive 2026-07-31, audited across the app that day). Wherever two actions stand together — a row or a column, a popup or a page — the one that is NOT the offer is passed on the way and the filled purple ENDS the block, under the thumb, the last thing read. Every pair in the app obeys it: `ConfirmDialog`'s cancel→confirm, home's invite card decline→accept, the group and account popups (below), and chat's leave/block popup, which led with the purple until this audit and was turned. **The one exception is the empty-Circles hub** (`HubStart`), where the purple LEADS and stays leading (user directive 2026-07-31, put back the same day it was turned): those are not two answers to something the app asked, they are two WAYS FORWARD off an empty page, the purple carries the reason line that explains it, and the first thing read must be the one being recommended. A pair of EQUAL choices is not this rule either (chat's reply/copy `SheetActionRow`s), and neither is a lone button.

**A SURFACE'S FOOT IS WHAT I MAY DO BESIDE WHAT I AM BEING OFFERED** (user directive 2026-07-31) — stated once as **`SheetActionPair`** and worn by the four surfaces that end this way: the **group** popup (where the group says more about itself + leave / take a request back / dismiss a refusal, over sharing the invite link or joining), the **account** popup (delete the account, beside signing out), **chat's leave/block** popup, and a managed circle's **roster page** (user directive 2026-08-02: preview the circle — the app's own `GroupsIcon`, since what opens is the CIRCLE as everyone else meets it — beside the purple that hands its link on; it takes `flush`, because the gap over it is the page's own `ownedFill` MD and not a popup's `SHEET_GAP.actions`, and it is why the share button's word is `communities.share` and not the full `shareInvite` sentence the popup's full-width button carries). **That preview opens with `status='joined'`, my real standing** (user directive 2026-08-02): the roster behind it lists me, so an APPROVER leaves his circle from there like anyone else — opened as `none`, the way the settings bar's preview was, the popup read me as a stranger to a circle I help run. **The OWNER may not leave, and that guard is the POPUP's** (`iOwnIt` in `GroupSheet`, user directive 2026-08-02: he transfers ownership first) — `app_leave_group` deletes the membership row and nothing more, so an owner walking out would strand the circle, which is the same rule `MemberProfileView` keeps for my own card. It is answered two ways because either alone is wrong: `GroupBrief.is_owner` (a managed row spreads it straight in) covers the moment before a roster has said who the owner is, and matching the drawn owner against my own id covers every host that has no such flag. That page is the one host that is not a popup, and the shape is unchanged by it: a foot is a foot. What I MAY do leads as bare marks on no ground at all — `OptionStrip` options, glyph over word, no tile — and the ONE action the popup is asking for ends the block in the app's purple, under the thumb. **There are two arrangements and the call site states which** (user directive 2026-08-02): BESIDE (the default) is one row — the strip hugs its own words at the START, the purple takes the rest, and standing beside an option it wears that option's shape (`Button`'s `stack`, injected BY the row, so a call site cannot state it wrongly), the fill being the only thing telling the pair apart. **`stacked` exists for a strip of more than one**: the strip is the whole row with its options dividing it evenly, and the purple runs the full width UNDER it as an ORDINARY button, its mark beside its label like every other button in the app. What decides between them is how many options there are — a strip of two hugging beside a purple tile leaves each side a third of the popup. **The group popup passes it whenever the circle has a LINK** (user directive 2026-08-02, evening): **"לפרטים נוספים" is an option of that strip** — a `GlobeIcon` over one word, LEADING — and it is the **ONLY** thing in the app that opens a circle's link. The popup's HEAD is a plain, dead block of writing again (the `Pressable` around `GroupHead` of 2026-07-29 is gone): a face and a name that happen to be pressable say nothing about a link behind them, so a circle that had written down where to read more looked like a circle that had not. The option was deleted for half a day on the "the head is already that door" reasoning and put straight back — the mark is the point. It is drawn only when `group.link` exists. **And that popup is ALWAYS `stacked`, at every option count** (user directive 2026-08-02, evening): the options divide the row and the purple runs the full width UNDER them, so "more details" always stands ABOVE the share line and the invitation is always an ORDINARY button — mark beside label, at the label's own size — never the mark-over-a-small-word shape. What a circle's foot looks like may not change with how many things I happen to be allowed to do in that particular circle. Nothing else about the foot is a call site's: the gap above it, the case where one side is missing and the case where neither is are the component's. **The drastic action is the one with NO ground** (the account popup's delete and chat's block, 2026-07-31): each used to be a muted `secondary` tile stacked with the purple, but a tile is a tile, and the thing you must never press by accident was still painted as something to press. The guard is the question the popup itself asks, not a softer fill. A popup that is a `ConfirmDialog` is untouched by this — that is a question being answered, and it keeps `SheetActions row`.

**AND THE POPUP ASKS ITS QUESTION ONCE** (user directive 2026-08-02). A popup raised by a NAMED action has nothing further to ask: the user pressed "End chat", so what the surface owes him is a title, the sentence saying what ending a chat does, and the two answers — and each answer FIRES on the tap. Chat's leave/block popup was a bare `flush` row of two buttons that each handed over to a `ConfirmDialog` repeating the identical question ("End chat" → *End chat?*), so the one thing the user had already decided was put to him twice, through two Modals chained on `onClosed`. It is the ordinary popup now: `SheetTitle` (`home.leaveTitle`) + `SheetDesc` (`home.leaveDesc`) + the pair, with `runAction` on both sides — the block gets the strip's own `busy` spinner in its glyph's place, the leave gets the button's `loading`, and neither is `disabled` by the other's flight (`runAction`'s `busy` guard already swallows the tap, and a sibling greying out for a few frames is a flicker, not information). One popup's worth of copy survives it: the block's own title and paragraph, and both confirm labels — which named the same two actions a second time — are deleted from `he.ts`/`en.ts`, and the leave/block pair is no longer a `flush` call site (chat's reply/copy `SheetActions` is the last one). The user is told what he is doing; he is not asked to agree with himself.

**AND THE POPUP IS CLOSED BY THE ANSWER, NEVER BY THE TAP** (user directive 2026-08-02). Any press that rewrites the user's state — cancelling an invitation, declining one, ending a chat, leaving a circle, clearing a card that is over — HOLDS the surface it was taken on, with the pressed button's own spinner in it, until the server has answered; only then does the popup go and only then does the screen express the new state. The alternative, which is what three call sites in `home.tsx` did, is the app showing the outcome a whole round trip before it is a fact: a refusal (the RPCs' own refusals are 400s) or a dropped invoke left the user looking at a board that had never changed, with the surface he decided on already gone. `runAction`'s **`onDone(ok)`** is the mechanism and it is the only one — the close belongs in that callback, never beside the call — and an action that outlasts its own request (the accept, held until the chat lands; the send, held until Realtime flips page1 to `waiting`) holds the spinner for the whole of it rather than for the invoke. Deleted with the old shape: `runCancel`'s up-front `setMessageOpen(null)` + `setDisplayedMatch(null)`, and the `setMessageOpen(null); pageNBack()` pairs on the two terminal cards.
**AND A HELD POPUP HAS NO WAY OUT AT ALL, IN ALL THREE DIRECTIONS AT ONCE**: `BottomSheet`'s **`busy`** — the old `disableBackdropDismiss`, which every one of its four call sites passed `busy` to anyway and which shut only the backdrop tap and hardware back, leaving the user free to DRAG away a popup whose request was still out. It now shuts the swipe with them (`.enabled(swipeToDismiss && !busy)`). A call site whose action outlasts its request passes that fact here too, not only to the button.

**AND THE CARD'S MESSAGE IS ONE OF THOSE POPUPS** (user directive 2026-08-02, the same rule reaching page1's waiting card). "Cancel invitation" in `CardMessage` **fires** — `onPress={runCancel}`, with the button's own `loading` while the invoke is out — instead of closing and chaining an intent through `onClosed` to a `ConfirmDialog` that said the same three words back ("ביטול הזמנה" → *לבטל הזמנה?*). The popup it stands in is already the whole question: `home.waitingTimerTitle` names the state and `home.waitingTimerDesc` says what the invitation is costing while it stands, which is exactly what the confirm's paragraph was for, and putting the popup away is the other answer. **And the DRAG lands on that same surface**: a committed pull on a waiting card (`pullCommitRef`, `commit:'snapBack'`) raises the card's message rather than a confirm of its own, so the gesture still ASKS a named cancellable question — the invite card's rule of 2026-08-01 — and asks it in the one place the heading chip's mark opens. Deleted with the dialog: `cancelConfirmOpen`, the `'cancel'` arm of `messageIntentRef` (only `'buy'` is left, and it survives because the buy picker is a genuine second Modal rather than an answer to this question), and `home.cancelWaitingTitle` / `home.cancelWaitingDesc*` / `home.cancelWaitingConfirm` from `he.ts`/`en.ts` — `home.cancelWaitingBtn`, the one label on the one button, is what remains.

**The rhythm is `SHEET_GAP` in `tokens.ts` and nothing else** (user directive 2026-07-30, read off the invite popup — the user sent that popup as the reference): `title` LG above the popup's first block (under the drag handle, whose own band is MD/`SHEET_GAP.title`; a handle-less popup takes it as the card's `paddingTop`), `desc` SM under the title — a title and the sentence explaining it are ONE block — `block` MD between two body blocks (a field, a toggle, a list), `actions` XL above the button row, the popup's widest gap on purpose, so the eye reads "what this is" and then "what I can do". The bottom is the rule above. **A popup body declares no vertical spacing of its own**, and a title never declares a `marginBottom`: the gap belongs to whatever comes NEXT, because only that thing knows which gap it is. Before this, the gap over a button row was MD in `ConfirmDialog`, LG in the groups sheet, XL on the invite card and SM in the group popup, and the gap under a title was SM, XS or nothing depending on the file.

**The gutter is the card's too** — `paddingHorizontal: MD`, one indent for every popup (it was LG in `ConfirmDialog`, MD elsewhere, MD-inside-MD in the groups sheet). `contentStyle` exists for the few bodies that genuinely are not a text column and may override **only** the frame: `paddingHorizontal: 0` for an edge-to-edge row list (the select lists, the location steps), `SM` for a grid/column of full-width tiles (chat's message actions, the family sheets), plus a `flex`/`flexShrink` a tall body needs. A `paddingTop` or `paddingBottom` there is a bug.

**A MENU OF VERBS ABOUT THE THING JUST TAPPED IS NOT A POPUP — IT OPENS WHERE THE FINGER IS** (user directive 2026-07-31). A popup is a surface the app RAISES to say something, and it earns the bottom of the screen, a title, a paragraph and a row of named buttons. A contextual menu says nothing at all — it is the tapped object's own set of verbs — so it is a little tile that grows out of the tap and stands over it: **`mobile/src/components/TapMenu.tsx`**, the app's one surface that is not a `BottomSheet`, and the only one that may ever be. It takes `at` (a touch's own `pageX`/`pageY`, held in state at the call site so the point cannot change identity under an open menu) and `actions`.

**It is ONE WHITE TILE with the app's hairline across it, and every row is a GLYPH AND A WORD** (user directive 2026-07-31) — literally `ChipStack` `onPhoto`, the very object the match card's fact set is: one set of verbs about one thing is one object, exactly as one set of facts about one person is. It spent an afternoon as four separate icon-only tiles laid out as a cross around the finger; separate tiles read as separate things, and a bare mark makes the reader guess at what it does. **ONLY WHAT IS AVAILABLE IS SHOWN** (user directive 2026-07-31), and that is the app's one exception to `DISABLED_OPACITY`: a shut control normally stays on screen because it is a door the user will want and must be told about, but "move this photo up" when it is already first is not a door being held shut, it is a thing that does not exist for this photo, and a menu of three has no room to explain. The caller passes what applies and the tile is exactly that tall.

**The pop is a ZOOM AND NOTHING ELSE** (user directive 2026-07-31): scale 0 → 1 with `transformOrigin` set to the finger in the tile's own coordinates, and **no opacity anywhere in the file** — the zero start is also what hides it before it has been measured, so there is nothing that could blink on, and nothing that puts a translucent shadowed tile into an offscreen compositing layer over a photograph (which is what made the separate tiles flicker on Android). It carries **no scrim** either — dimming the screen would say a surface had been raised, which is precisely what this is not; the backdrop is only there to catch the tap that puts it away. **The safety margin is the page's own**: the tile is centred on the finger's column, stood `SM` clear of the finger (above it where there is room), and then pushed back inside the page gutter (`MD`) and both safe areas, so a photo tapped at the edge of the screen still opens fully on-screen. **And it is never WIDER than that band either** (user directive 2026-08-01): a row is a line of text, so a `maxWidth` of `screenW − 2·MD` is what makes the sentence wrap inside the tile instead of hanging off the screen (the first-open tutorial came up clipped at both ends). The horizontal placement is a **transform**, not a layout `left`, and that is what makes the cap measurable at all: Yoga hands an absolute box `parentWidth − left` to lay itself out in, so a `left` computed FROM the measured width feeds back into the width — the tile wrapped, moved, re-wrapped wider, moved again, over several renders with the zoom already running. Pinned at `left: 0` the available width is the same on every pass and the tile is measured once, then translated (the zoom's origin is unaffected — the translate rides outside the scale).

**And the window it is measured in is pinned LTR** (`styles.window`, user report 2026-07-31: in Hebrew the menu opened mirrored, on the wrong side of the finger). `left` is NOT a physical edge for an absolutely positioned box — Yoga resolves an absolute child's cross-axis position against its parent's direction, so in an RTL container a `left` is read as the TRAILING offset and measured from the right edge, which mirrors a point that came from a touch and is physical by definition. The tile's rows still read start-to-end: a `Chip` states its own direction.

Its call sites are the own-profile card's **photo actions** (`PreviewFieldPage`): **show photo**, move up, **replace**, **add a photo**, delete, move down, top-down — and the one-row **tutorial** below, which is that same menu. **Showing it LEADS** (user directive 2026-08-04) and is the one row that is not an edit at all — it takes the info set OFF the photo, which is what a bare tap does on every other card (see the toggle rule above); it is always listed, since every photo can be looked at, and it closes the menu on the tap. **Adding a photo is a row here** (user directive 2026-08-01), directly under Replace. It is the one row that is not ABOUT the photo under the finger, and it earns its place anyway: a photo is where the user's attention already is when he wants another one, and this menu is the whole of what the app has to say about photos now that the profile's plus is gone. It is absent at the six-photo ceiling, by the same "only what applies is listed" rule the moves and the delete follow, and it closes the menu on the tap, exactly as Replace does (see the spinner rule below).
**AND IT TEACHES ITSELF, ONCE** (user directive 2026-08-01): the first time the own-profile preview opens, this menu pops with a SINGLE row saying to tap a photo (`settings.photoMenuHint`), anchored at the middle of the window since there is no finger to anchor to. Tapping that row — or a photo, which spends the tap on the lesson and nothing else — puts it away, and `SEEN_FLAGS.photoMenuSeen` means it never comes back. It is the one thing in the app that raises a surface to teach something, and it is admitted because it is barely a surface: `TapMenu` has no scrim, dims nothing and goes away on any touch at all, so it reads as a label standing on the photo rather than as the app taking the screen. Do not read this as licence for a second tutorial anywhere else — see the dock rule, where a counter and a forced popup were deleted for exactly the reasons this one avoids. It was a `BottomSheet` of four labelled tiles until 2026-07-31 — a whole surface raised from the bottom of the screen to say four words about the photo the user had just put a finger on — and the SURFACE is what changed; the LIST did not. **Replace was dropped with that popup on the reasoning "replacing a photo is deleting it and adding one, and both are one tap away", and the user put it back the same day** ("there was such an option and it worked great"): it is the one edit that leaves the ORDER of the photos — which is what the card reads top to bottom — untouched, so it is not the delete and the add standing either side of it. It sits directly under "move up", where the old popup put it; it is the one row that is always listed (every photo can be swapped); and it closes the menu on the tap, exactly as the add-photo row does. (`PhotoEditor`'s grid keeps its own separate replace; there a photo IS a slot.) Do not give this a title, a scrim, a disabled row, or a second call site that is really a dialog.

**A SPINNER IS FOR THE UPLOAD, NEVER FOR THE PICKER COMING UP** (user directive 2026-08-01). Opening the OS gallery is not the app working on anything — the picker is its own answer to the tap, and it arrives over whatever raised it — so nothing is drawn for `launchImageLibraryAsync`'s cold start, anywhere. The spinner belongs to the one thing the user cannot see for himself: the photo going to storage and the row being saved. Three places drew one and none does now: the photo menu's **replace** and **add** rows (they stayed open with a spinner in the row's own glyph; they close on the tap now, like every other row in that tile), `PhotoEditor`'s grid (a spinner in the tapped "+" slot and a white scrim over the cell being replaced — the onboarding photo step, which is where the user saw it), and **chat's** attach strip (a spinner in place of the image tile's glyph; the strip closes on the tap, and the pending BUBBLE is what says the picture is being sent). What each of them still needs is the re-entrancy guard, and that is a **`pickerOpen` ref** in all three — never state: a second picker must be refused, and refusing it is not a reason to re-render. `PhotoEditor`'s uploads-in-flight spinner stays; that one is an upload.

## A glyph beside text — `GlyphSlot`, never a line box computed in JS

Single source for standing an icon next to a label: **`GlyphSlot`** (`mobile/src/components/GlyphSlot.tsx`) — the chip's leading and trailing glyphs, the settings row's leading glyph, the button's start icon. Never hand-roll a wrapper with a `height:`/`marginTop:` derived from `lh(...)`.

- **The probe itself is `LineProbe`** (same file) — the one way anything in the app asks how tall a real line of text is. `GlyphSlot` lets it set the height of the box it centres a glyph in; a caller that needs the number reads it back via `onHeight`.
- **The slot's height comes from an invisible one-character `Text`**, not from arithmetic. `lineHeight` is NOT knowable from JS: Android 14+ runs it through the OS's non-linear font-scale curve and does **not** cap it with `maxFontSizeMultiplier` (only `fontSize` is capped), so at font_scale 2.0 a 22dp line box renders ~37dp. Every computed box therefore put its glyph high on a large-font device and slightly low at font scale 1 (2026-07-29). The probe is measured by the same text engine that draws the label, so it is right by construction on every OS version, density and font scale.
- **The one correction that stays computable is `inkOffset`** (`mobile/src/fonts.ts`): a line's ink centre sits `((A−D)/2 − inkHeight/2) · fontSize` below its line box centre, and the line height cancels out of that. `A`/`D`/cap height/Hebrew letter height are read from the bundled NotoSansHebrew files, not tuned by eye; Hebrew ink stops 0.114 em lower than Latin, so the constant follows the SCRIPT — and it is **the LABEL's script, not the app's** (user report 2026-07-31). It followed the app's direction for as long as "the UI renders one language at a time" held, and a label is not always UI language: a person's NAME is user data, so the match card's heading chip paints "Inbal, 51" in a Hebrew build and the report shield beside it was being centred on Hebrew ink that line does not carry (measured on a font_scale 2.0 device: the glyph sat 1.3dp — 4.5px — below the name's own cap-ink centre, while a glyph beside a genuinely Hebrew label on the same card was exact to the pixel). So `GlyphSlot` takes a **`label`** and hands it to `inkOffset`, and the line answers for itself: **a line's ink is its TALLEST ink** (user report 2026-08-04, correcting the "any Hebrew letter and it is a Hebrew line" test this shipped with), so a label carrying anything that rises to cap height — a Latin letter **or a DIGIT** — is a cap-tall line whatever else is in it, and only Hebrew letters ALONE take the Hebrew constant. It is not a question about what the sentence IS, it is a question about the band the eye reads: "אופיר, 44" paints ink to 0.714 exactly as "Inbal, 51" does, and the mark beside it was centred on the 0.600 Hebrew body, ~1dp low against the very chips under it on the same card. A caller with no label to give keeps the app's direction as the fallback. Four callers pass one today: the chip (its own `text`/`segments`, for all three of its slots), the button (its label), the settings row (its label) and `SheetHeader` (its title, as often a group's name as a UI string). It returns a float — rounding it to whole dp is what used to collapse two different font scales onto the same nudge.
- **A glyph never outgrows its label**: `GlyphSlot` declares the label's own `maxFontSizeMultiplier` as the glyph's `GlyphScale` ceiling — which, since the app has exactly one, is `FONT_SCALE` for every glyph that stands beside text.
- **A CHIP IS EXACTLY A ROUND CHROME BUTTON TALL** (user directive 2026-07-30), by the same measurement. A chip tile and a round button are the same white object — the card's name/age and "End Chat" chips sit directly beside home's hamburger — so `CHIP_HEIGHT` **is** `ROUND_BUTTON_SIZE_SM`, and what `Chip` derives from it is its **vertical padding**: half of whatever room the button's diameter has left once the label's measured line box is in it (`chipPad`, floored at 0, so nothing is ever clipped and a wrapped label still grows by whole line boxes). A fixed `paddingVertical: SM` made that height at font scale 1 and at no other scale — the chips came out ~25% taller than the hamburger beside them at font_scale 2.0. **Two variants opt out**, each for its own reason: the `small` tile is deliberately a step UNDER the chrome rather than level with it, and keeps its token box; a chip that is a **BLOCK** rather than a pill pays the gutter on the vertical too (`CHIP_BLOCK_PAD`, below);.
- **A CHIP THAT IS A BLOCK PAYS THE GUTTER ON EVERY SIDE, AND ITS OUTER EDGES ARE NOT ITS SEAMS** (user directive 2026-07-31, restored 2026-08-02). One number on all four sides: `CHIP_BLOCK_PAD` = `CHIP_GUTTER` (`MD`), so a block indents its text from its own rim exactly as every pill does. It is taken by the match card's merged fact tile (every `ChipStack` row) and by its **bio tile**, which imports the constant rather than re-typing it so the two can never drift. The pill rule above is right for a tile carrying one short line; the bottom-START set is not that — it stacks wrapping sentences and a paragraph — so it does not take the derived ~8dp. It spent an afternoon on 2026-08-02 at a step in (`SM`) on the vertical, on "at the ends of a stack of facts the gutter reads as a band of empty white", and the user asked for the bigger padding back the same day: the tighter tile read as crowded against its own edges. **Do not close the vertical in again**, and there is no per-axis constant to bring back. **A SEAM is half a GUTTER, because two rows pay it together** (`CHIP_BLOCK_SEAM_PAD`, stated off `CHIP_BLOCK_PAD` and untouched through both passes — the user asked about the block's own edges and excluded the dividers in the same breath): the hairline between two facts has a row's padding on EACH side of it, so the full gutter twice over opened a band wider than the tile's own edges and read as three tiles again — the very thing the merge undid. How far two facts stand from each other is a different question from how close the stack runs to the tile's rim. The stack tells each row where it stands (the `ChipStacked` context carries `{first,last}`); a row never infers it. A LONE pill is untouched.
- **A MARK IN A TILE IS CENTRED IN THE TILE, NEVER ON A LINE OF TEXT** (user report 2026-07-31). `GlyphSlot` is for a glyph standing BESIDE a label and it pays for that neighbour twice — its box is one LINE tall rather than the tile's, and `inkOffset` then nudges the mark down onto ink that is not there — so a tile whose whole content is a mark visibly missed its own middle. The one of these is the purple `endAction` block's glyph form (the own-profile card's plus), centred by plain flexbox like the close X in a round button. That block also carries a `minHeight: CHIP_HEIGHT` FLOOR under its `alignSelf:'stretch'`: the chip's row is aligned flex-start, so that stretch is a per-child override — the very kind Fabric is known to drop silently on this component — and dropped, the purple stood short of the tile's bottom edge, which is what made the mark inside it read high. (An icon-only `Chip` had the same problem and a `markOnly` variant for it; the photo menu says its rows in words now, so nothing in the app is one. Note if one ever returns: the label branch renders its `Text` unconditionally, so a chip with no label still lays out an EMPTY one — and the row's `gap` for it, which pushes the mark half a gap off centre.)

## Font scale — ONE ceiling for the whole app, and it is `FONT_SCALE`

**Every string in the app grows by the same factor and stops at the same place** (user directive 2026-07-30). `FONT_SCALE` in `mobile/src/fonts.ts` is a single number (**1.15**), applied **once**, in `AppText`'s `Text`/`TextInput` wrappers. **No call site passes `maxFontSizeMultiplier`** — after this landed the prop survives in exactly two places: that wrapper, and `GlyphSlot`'s invisible `LineProbe`, which is a measuring stick rather than painted text and must be able to measure at its glyph box's ceiling.

It replaced a three-class ramp (`ui` 1.0 / `heading` 1.15 / `body` 1.3) whose classes silently re-ranked the design the moment the OS slider moved: the *same* `SHEET_TITLE` came out 26dp on the communities sheet header (`body`, inherited from `AppText`) and 23dp on home's status card (`heading`, passed by hand) — two headings of identical declared rank at different sizes — and a heading capped at 1.15 standing over a description capped at 1.3 closed the 20:16 gap that is the only thing saying which of the two IS the heading. A ratio the design states in `TEXT.*` must hold at **every** OS setting, which one ceiling gives and a ramp cannot.

- **NO text style declares a `lineHeight`; the leading is the FONT's** (user directive 2026-07-30, same root cause). A declared `lineHeight` is a dp number, and Android grows text metrics through the OS font-scale curve **uncapped** by `maxFontSizeMultiplier` while `fontSize` **is** capped — so above the ceiling the leading runs away from the ink: a 16/22 body paragraph on a `font_scale=2.0` device painted 18.4dp of ink inside a ~37dp line box, a leading of 2.0 em where the design says 1.4 (reported on Hebrew_Big, 2026-07-30). Leaving it undeclared hands the box to the bundled font's ascent+descent — `FONT_LINE_RATIO` in `mobile/src/fonts.ts`, **1.36 em** — which is a multiple of the size the device actually painted and so is identical at every OS setting. It was within half a dp of the old 1.4 at font scale 1, so nothing moved on an ordinary device. `lh()` in `tokens.ts` survives ONLY as an **estimate for sizing a box in JS before its text exists** (a skeleton row, the composer's max height, a header's first frame) and now uses that same font ratio; it is never a `lineHeight`. Where a dp of error matters, **measure** with `LineProbe`. The only declared line boxes left in the app are two single glyphs whose box IS the glyph (the ✓ in the 20dp checkbox, the × on a kid chip) — they state no leading at all.
- **The single exception to the ceiling is geometry, not type: `FIXED_BOX_SCALE` (1)** — a glyph centred in a box whose dp does NOT follow the font scale: `RoundButton`'s circle (so every in-circle icon in the app) and home's centre-notice circle, where a growing glyph would change the one `ROUND_BUTTON_GLYPH_RATIO` per device. **Never for text** — no label in the app lives in a fixed box (every label container is content-sized or `minHeight`), so a button label or a timestamp pinned against the slider is a bug, not a protection.
- `allowFontScaling={false}` is banned for the same reason, everywhere.

## Colour — purple and white, nothing else

`mobile/src/colors.ts` is the ONE source of colour; no component may declare a hex/rgba of its own.

- **The palette is PURPLE + WHITE** (user directive 2026-07-28). There is **no beige** (the whole warm scheme was removed that day), no grey, no red, no second accent hue. Every muted step is INK laid translucent so a surface can never drift to neutral grey; the only black is `SHADOW_BLACK`, and only for shadows/scrims.
- **Names state ROLE + STRENGTH, never a hue** (user directive 2026-07-28). The old `GREEN` / `ORANGE` / `BLACK` / `PRIMARY` / `BG` names are gone and must not come back — they named a colour the value had not been for months. Current set: `PAGE` / `SURFACE` / `SURFACE_SUNK` / `LINE`; `INK`, `INK_PRESSED`, `INK_MUTED`, `INK_PALE`; the alpha ramp `INK_BODY` → `INK_SUBTLE` → `INK_HINT` → `INK_DIM` → `INK_WASH`; `WHITE` + `WHITE_STRONG` / `WHITE_MID` / `WHITE_SOFT`; role aliases `PHOTO_CHROME`, `STATUS_BAND`, `PRESENCE`, `NEGATIVE`, `PREMIUM`, `SELECTION`. A new colour name must say what it is FOR, not what it looks like. There is no icon-only hue any more either: the old `BRAND_MARK` #6C3FB2 is deleted and the brand mark is drawn in `INK` (user directive 2026-07-28).
- **`PAGE` is the page, `SURFACE` (white) is what lifts off it.** `PAGE` paints only a page root that carries white CARDS or a photo (home, chat, communities). **Every POPUP is white** (user directive 2026-07-28) — set once, on `BottomSheet.tsx`'s `card`, which `ConfirmDialog` / `BuyExtraPopup` / `SharedGroupsPopup` / every action sheet compose; `OverlaySheet`'s rising card is `SURFACE` for the same reason. Cards, chips, rows, fields and buttons take `SURFACE` too.
- **`mobile/scripts/build-icons.mjs` is the sync tool for everything that cannot import `colors.ts`**: it parses the tokens and writes the icon/splash/favicon/og art, `app.json` (splash + adaptive-icon + notification tint), **`web/public/tokens.css`** (the site's entire palette — the site declares no colour of its own) and every static page's `theme-color` meta. `build-feature-graphic.mjs` does the Play feature graphic from the same tokens. Re-run both after any token change, and never hand-edit those colours in `app.json`, `tokens.css` or an HTML meta.
- **A soft tile is the `PAGE` tint** (user directive 2026-07-28): every chip, pill, filled row, secondary button and press-flash that used to wear the old 10%-alpha `INK_HAZE` is `PAGE` now, and that token is DELETED. The two jobs `PAGE` cannot do went to the tokens that own them: a hairline is `LINE`, and a control that must stay legible on white (a drag handle, the Switch OFF track, an upload placeholder glyph) takes `INK_DIM` / `SURFACE_SUNK`. A chip on a PAGE-tinted surface inverts to white (chat's incoming bubbles).
- **The settings surfaces are white** (user directive 2026-07-28): in `SettingsSurfaces.tsx` the profile preview's `previewWrap` is `SURFACE`, matching the sheet it rises in (the menu page that also carried `rootOuter` / `scrollBody` is deleted; its popups are white by `BottomSheet`'s own card). A page that carries white CARDS (home, chat, communities) keeps the `PAGE` tint, because that tint is what makes a white card read as lifted.

## i18n text style

Do **not** use em dashes (—) in any i18n string (`mobile/src/i18n/he.ts`, `en.ts`). Use a period, comma, or colon.

**THE PRODUCT WORD IS "מעגל" / "circle", AND "קבוצה" / "group" IS NOT A WORD THE USER READS** (user directive 2026-08-01). One term for the thing people join, in both languages, on every surface: the app, the push bodies in `supabase/functions/global.ts`, and the site (`web/public/`), which had been saying מעגלים for weeks while the app titled its hub "המעגלים שלי" over a page of קבוצות. `group` survives as an **identifier only** — the `groups` / `user_groups` tables, the `group_*` push codes and their `{group}` placeholder, the `/g/` invite link, the i18n KEY names (`communities.newGroup`, `removeFromGroup`, `settings.groupsLeave*`), component props — so a key whose name says group and whose value says מעגל is correct and must not be "fixed". Three things the rename settled, each a user directive of the same day, and none of them to be undone by a later literal translation:
- **מעגל is masculine where קבוצה was feminine**, so every word agreeing with it turned too (`מנוהלת`→`מנוהל`, `מופיעה`→`מופיע`, `תעבור`→`יעבור`, `בה`→`בו`). The strings that carry no noun at all are the ones a search misses.
- **The kind picker names the JOINING, not the circle** — `הצטרפות פתוחה` / `הצטרפות באישור` / `מעגל פרטי` (`Open to join` / `Approval required` / `Private circle`). "מעגל מאושר" reads first as a HAPPY circle, which the feminine got away with and the masculine does not; private stays a fact about the circle because visibility is what that stop changes.
- **"מעגל" is never used in the ABSTRACT sense any more** (somebody's social circle). Once a circle is a THING in the app, "המעגל שלך" / "מהמעגלים שלהם" read as objects on the screen the user is looking at, so the empty-hub title counts them (`כאן מתחילים המעגלים שלך`) and every sentence about what a friend brings names the PEOPLE. Same in English.
- A circle **does not approve** anything (`ממתינה לאישור`, not "לאישור של המעגל"), and the WhatsApp share message names the app because it is read by people who have never opened it (`הצטרפו אל {name} באפליקציית Once`).

**AND THE CODE SAYS `circles` TOO — EXCEPT ON THE WIRE** (user directive 2026-08-02). `communities` was the developer-facing word for the same thing, so the app read one way and was written another. It is `circles` now everywhere a developer reads it: `mobile/src/lib/circles.ts`, `CirclesPage.tsx`, `CircleBits.tsx`, `circlesSummary` / `CirclesSummary` / `CirclesTarget` / `routeToCircles`, the `'circles'` overlay kind, and the **i18n key prefix `circles.*`** (every key was `communities.*`; `t()` takes `keyof Translations`, so a missed one is a compile error rather than a missing string at runtime — which is what made the sweep safe to do at all). **Three names did NOT move, and must not be "fixed":**
- **`users.relations.communities`, the JSON key** — the published build reads it out of the user row and the DB's own trigger writes it. Renaming it empties the hub, the dock's counts and its dots on every device until it updates: an Expand → Migrate → Contract staged over weeks in exchange for a name nobody sees. The reason is stated at the one place that reads it (`circlesSummary`).
- **The DB's `_communities_summary` / `_refresh_communities` / `_users_keep_communities` and the `comm_*` triggers** — internal, called from the bodies of many RPCs, and Postgres would not catch a missed reference until it ran.
- **`group`**, exactly as above.

**A SENTENCE CARRYING USER DATA IS PINNED TO THE UI'S DIRECTION — `pinDirection` in `mobile/src/i18n/index.ts`, never a style prop** (user report 2026-07-31: "Yoav בקבוצה מאז 30.7.2026" came out laid left to right, the date wedged between the name and the words that belong to it). Both platforms resolve a paragraph's direction from its FIRST STRONG character, so a Latin name at the head of a Hebrew string turns the whole line around; and `writingDirection`, the style prop that would say otherwise, is **iOS-only** (see `fonts.ts` — Android goes by the string's own script). The one thing both platforms read is the string, so the direction is stated IN it: an invisible RLM/LRM at the head, written as a `\u200F`/`\u200E` **escape** and never pasted in as the character. It is only for a sentence with a `{name}` (or any other datum the app did not write) in it — a string the app wrote whole already starts with its own script — and it wraps the sentence **after** the substitutions, so a datum that turns out empty leaves the mark on a sentence that still reads.

**No sentence-final period** (user directive 2026-07-28). In every text a user reads, a period is allowed **only when more text follows it on the same rendered line**. A period with nothing after it on its line is banned: at the end of a string, immediately before a `\n` inside one, at the end of a paragraph / heading / list item / chip, and before a `<br>`. So `'לא קטלוג. לא צ׳אטים אינסופיים'` keeps its middle period and drops the last; `'מפגשים אמיתיים\nממש קרוב\nבזמן אמת'` carries none. `?` and `!` are untouched, and a trailing ellipsis (`מחפש...`, `A sentence...`) is an ellipsis, not a period, so it stays (user confirmation 2026-07-28). **Code comments are exempt** — the rule is about displayed copy, not source prose.

It covers **everything the product shows, app and site**: `mobile/src/i18n/he.ts` + `en.ts`, any hard-coded UI string, the server's `PUSH_TITLE` / `PUSH_BODY` in `supabase/functions/global.ts`, and every page under `web/public/` — the landing copy in `index.html`'s `STRINGS`, `download.html` / `friend.html` / `group.html`, the `<meta name="description">` / `og:description` / `twitter:description` tags on all of them, the legal pages `privacy.html` / `terms.html` / `child-safety.html` (each language block, both the markup copy and the template-literal copy), and the admin console's `web/src/i18n/dictionaries/he.json` + `en.json`.

## DRY (single source of truth)

Every value and every UI element is defined **exactly once** and imported everywhere else.
- **Values:** any meaningful literal — sizes, colors, spacing, radii, durations, easings, z-indexes, gesture thresholds, velocity cutoffs, storage/query keys, route names, event/push codes, restriction keys, magic strings/numbers — lives in one named constant (design + motion tokens in the central theme module / `tokens.ts`; keys in a constants module). No inline literals at call sites. Two things that should "feel the same" reference the same token, not a re-typed `withTiming(..., {duration:350,...})`.
- **Elements:** every UI element exists once as a parameterized component. "Same thing with small differences" = one component with props, not two near-duplicates. Variants (size/tone/state) are props, never a forked component.
- **Behaviors:** animations, gestures, transitions, press feedback, swipe-to-dismiss, mount/unmount choreography are implemented once in a base component/hook and composed. No screen reimplements a behavior that already exists.
- **Timing:** prefer framework defaults (`withTiming(value)` with no config, `scrollTo({animated:true})`) over invented durations. Chain via completion callbacks, not `setTimeout` matched to a duration. Only add a named `MOTION.*` token in `tokens.ts` when a real choreography demands a non-default number, and reference it everywhere.
- Before writing a literal or a JSX block, search for an existing constant/component. Treat duplication you encounter as a bug to fix in the same change.

## Performance principles (server)

User-facing latency is the top priority. **Await only the critical path** (auth, the atomic state transaction, building the response body); everything else — `log`/`restrictions` inserts, push notifications, derived writes — runs via `EdgeRuntime.waitUntil(...)`. Each atomic transition is a **single RPC** (`BEGIN; SELECT … FOR UPDATE ordered by user_id; UPDATE; COMMIT`), not a sequence of `supabase.from(...)` calls; the ordered lock prevents deadlocks and replaces optimistic-retry loops. Push notifications are always fire-and-forget behind `waitUntil` — a failed push must never delay or fail the HTTP response.

## Logging

**Invariant: every HTTP request that reaches the edge function writes exactly one `log` row**, regardless of outcome. Missing rows are bugs. Funnel all DB access through `Tools.invoke(action, task, query)` (never call `Tools.supabase.*` directly from handler code — it bypasses the log). Every rejected precondition must go through `action.error(...)` so it appears as a log entry, not a silent 4xx. Wrap each atomic transaction as a single RPC / single `Tools.invoke` so it's one log entry.

## A BUILT PROFILE IS TWO PHOTOS

**`MIN_PHOTOS` photos, and nothing else** (user directive 2026-07-31). That is the whole definition of a finished onboarding and of a complete profile: **an empty bio is fine.** The bio used to be the marker — onboarding saved it last, so a non-empty bio doubled as "the flow ran to the end" — which made the one field nobody has to fill in the thing that decided whether the account worked at all, and it contradicted itself the moment the preview's inline editor let a built profile clear its bio back to null.

**The number is stated in exactly three places and they must agree**: `MIN_PHOTOS` in `mobile/src/lib/photos.ts` (read by `selectProfileBuilt`, the photo grid, the picker cap, the preview's delete floor and onboarding's step-4 CTA — it lives in `lib/` and not on `PhotoEditor` because the store may not import a component), `MIN_PROFILE_IMAGES` / `profileComplete` in `supabase/functions/app/index.ts`, and the `only_available` image filter inside `others()`. Change one and you change all three, in the same change.

**There is NO minimum bio length** — `BIO_MIN` and the `bio.min` string are deleted, and must not come back. Onboarding's Finish is live the moment step 5 opens; the preview's inline editor runs on `EditableText` with `min={0} allowEmpty`, so clearing the field and pressing Update is an ordinary save that commits `null`. A whitespace-only bio is no bio: `normalizeBio` trims it on the client and `app_save_profile` deletes the key server-side (`length(trim(bio)) > 0` else `new_data - 'bio'`), so an empty string never reaches the row. Nothing about a bio may gate anything again — not visibility, not inviting, not the dock's dot, not a resume step.

## Data model (pointer)

The two-board game logic lives entirely in `users.relations` (JSONB): `page1` and `page2` state machines plus top-level `last_add_at` / `availability` / `credits` / `push`. `page1`/`page2` are internal state, not UI screens. All actions are `POST /app/<action>` → one `app_*` RPC each, dispatched in `supabase/functions/app/index.ts`. The DB schema, RPC bodies, credits economy, availability gates (geo / notification-presence / test-user partition), and push-notification catalog are the source of truth **in the code/migrations** — introspect the live functions (`pg_get_functiondef`) and read the migrations rather than trusting a prose copy. Local `supabase/migrations/` filenames don't always match live applied history; author new migrations against the **live** function bodies. Reflect any schema/RPC change in the code and `BACKWARD_COMPAT.md`, per the backward-compatibility rules above.
